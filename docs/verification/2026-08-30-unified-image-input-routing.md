# 2026-08-30 统一图片入口路由验证记录

> 结论：相册与相机已经共用一个低心智图片入口；受控商品图的自动入库、识别不确定后的延迟询问、衣橱跳转和既有相机权限恢复均在 iOS 模拟器通过。真实 iPhone 上的 Vision 类别质量与真实图片误路由率仍待验证。
>
> 读者：继续开发 Adonis 图片入口、衣橱或创作链路的工程师与 AI。
>
> 阅读后的行动：在不增加模式选择器或资料表单的前提下，延续当前路由契约，并把真实设备与授权图片集验证作为下一步，而不是扩大自动识别声明。

## 产品契约

用户只需要给 Adonis 一张图片，不需要先回答“这是 OOTD 还是商品图”。相册和相机在读图后进入同一条本机路由：

| 输入证据 | 用户看到的行为 | 不会发生的行为 |
| --- | --- | --- |
| 干净商品图、类别明确且置信度足够 | 自动收进衣橱，显示“继续创作 / 去衣橱”结果卡 | 不要求选模式，不要求填写品牌、材质或尺码 |
| 像干净商品图，但类别仍不确定 | 先继续人物贴纸创作；只有创作失败且没有可交付贴纸时询问一次是否收进衣橱 | 不在上传后立即弹问，不把不确定类别写成事实 |
| 平铺图、OOTD 或其他图片 | 继续创作 | 不因画面中有衣服而跳转衣橱或中断当前意图 |
| 本机图片分析失败 | 继续创作 | 不把分析故障伪装成商品图判断 |

自动入库后的反馈卡会自动滚动到浮动 Tab Bar 上方，用户可以继续创作或直接打开衣橱。完全相同的图片沿用既有内容指纹复用，不重复创建单品。

## 路由与数据边界

路由版本为 `creation-image-intent-v1`。自动进入衣橱必须同时满足以下条件：

- 画面类型为商品图。
- 背景干净度至少为 0.78。
- 类别建议存在且不是“未分类”。
- 类别置信度至少为 0.72。

看起来像商品图、但缺少可采用类别的图片只保留为创作失败后的衣橱候选。平铺图不会获得该兜底询问。阈值比衣橱内部采用类别建议的普通门槛更保守，目的是降低无意自动入库，而不是证明分类已经准确。

自动入库复用衣橱现有的本地图片分析、媒体写入、SwiftData 保存、事务回滚、内容指纹去重和来源说明。它只建立衣橱单品，不会自动把某条 OOTD 关联为同一件衣服；身份级同款关系仍只允许用户明确确认。

创作页把读图、路由、人物贴纸生成和衣橱入库区分为不同操作状态。取消或超时时只记录当前真实操作；相机权限提示与商品图兜底提示共用单一提示状态机，避免 SwiftUI 中多个 item-alert 因修饰器顺序互相覆盖。

## 测试驱动过程

路由先由独立单元契约锁定，再接入界面：

1. 第一轮失败测试确认项目中尚无统一路由器。
2. 最小实现先支持高置信度商品图自动入库。
3. 第二轮失败测试暴露“无类别商品图被直接入库”，随后加入类别与置信度门槛。
4. 第三轮失败测试暴露“未分类建议仍可直接入库”，随后明确排除未分类。
5. 最终六个路由测试覆盖高置信度、无类别、未分类、0.71 边界、平铺图和稳定版本。

第一次整套 UI 回归还发现新增商品图提示覆盖了相机权限提示。将两类提示分别挂到不同视图后，相机恢复但商品图提示失效，证明单纯调整修饰器顺序不可靠；最终改为一个显式提示状态机。拒绝权限、系统限制与商品图兜底三条针对性 UI 流程随后同时通过。

## 仍未证明

- 当前 iOS 26.5 模拟器无法运行受测 Vision 推理。两条商品图 UI 流程使用仅 Debug 的干净商品图，并注入“上装”或“无类别”建议；它们证明路由和交互，不证明真实类别模型。
- 尚未在真实 iPhone 上用授权商品图、商品截图、平铺图和 OOTD 统计误入衣橱、漏入衣橱或错误类别。0.78 与 0.72 是保守工程门槛，不是用户数据验证后的最优值。
- 自动入库只表示“这张图很像可建档的衣物图片”，不表示已识别 SKU、品牌、材质、尺码、合身效果或与某条 OOTD 中的同款身份。
- 真实相机拍摄、首次权限弹窗、拒绝后设置往返和拍摄后的同一路由仍需真机验证；模拟器只验证了 App 侧可注入状态。
- 当前没有账号、云同步、购物链接解析、第三方识别 API 或付费图片服务。
