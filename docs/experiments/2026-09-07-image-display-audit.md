# 2026-09-07 本地图片展示性能只读审计

> 状态：已定位候选并完成 macOS ImageIO 对照测量；未修改 App 图片加载，未证明 iOS 卡顿或真机内存下降。

## 代码发现

`StoredImageView.body` 每次求值都会调用 `MediaStore.shared.image(filename:)`，后者直接使用 `UIImage(contentsOfFile:)`，没有展示尺寸参数、后台加载或缓存。这个通用视图同时用于衣橱网格、花历记录、数字展柜与详情。当前调用发生在 SwiftUI 视图求值路径中，文件读取与图片创建有重复发生的风险；UIImage 的解码也可能推迟到绘制阶段，单看初始化代码无法确定实际主线程耗时。

这是代码层面的性能候选，尚不能据此宣称滚动已经掉帧。与其先修改存储或分享格式，后续应先测量多条真实收藏的网格滚动，再只为展示层添加异步缩略图。

## 授权样片的独立对照

使用项目已有四张授权原图和三张 AI 透明贴纸，在 macOS 的 ImageIO 上分别读取完整图片、最长边 512 像素缩略图与 1024 像素缩略图。未写出或覆盖任何图片，读取后仅统计 `CGImage.bytesPerRow × height`。

| 输入 | 完整位图 | 512 像素位图 | 1024 像素位图 |
| --- | ---: | ---: | ---: |
| 四张 1080 × 1440 原图，每张 | 6,220,800 B | 786,432 B | 3,145,728 B |
| sample-01 AI 贴纸 | 4,982,784 B | 557,056 B | 2,228,224 B |
| sample-02 AI 贴纸 | 3,348,480 B | 376,832 B | 1,490,944 B |
| sample-03 AI 贴纸 | 3,422,208 B | 385,024 B | 1,523,712 B |

七张输入位图的算术合计从 34.94 MiB 降至 512 像素方案的 4.26 MiB。这里是返回位图行跨度的合计，不是进程 RSS、峰值分配、同时驻留量或 iOS 内存节省证据；尤其 PNG 生成缩略图时仍可能需要更大的中间解码缓冲。单次计时受当前并行构建影响，只归档原始数据，不据此报告提速比例。

完整源码、输入哈希、尺寸、位图字节数和原始计时见 [机器可读记录](../evidence/image-display-audit-2026-09-07.json)。实验使用 `CGImageSourceCreateImageAtIndex` 与 `CGImageSourceCreateThumbnailAtIndex`，并要求创建时解码；相关参数见 Apple 的 [即时解码说明](https://developer.apple.com/documentation/imageio/kcgimagesourceshouldcacheimmediately)与 [缩略图最大像素尺寸](https://developer.apple.com/documentation/imageio/kcgimagesourcethumbnailmaxpixelsize)。

## 后续改动应保持的边界

- 缩略图只服务展示，存储、透明贴纸导出、相册写入、分享卡和生成输入继续读取原始尺寸资源。
- 加载在后台完成；视图切换文件时取消旧任务，迟到的旧图片不能写回新单品。
- 缓存应有内存上限，并处理删除、补商品图、同名重写和清空数据；不新增持久化缩略图或未声明的数据副本。
- 需要验证 Alpha、方向、长宽比、透明背景、缺图、空态和放大后清晰度。只降低位图尺寸不能代替视觉验收。
- 真正实施前按 AGENTS 阅读本地数据与相关页面的验证记录；实施后完成静态分析、有关无障碍/持久化/图片回归，并在同一设备、同一数据量和同一滚动动作下比较指标。

当前不勾选产品性能目标，不修改原始媒体或回归基线。先解决本轮全量 UI 测试暴露的分享面板退出问题，再决定是否推进此展示层改动。
